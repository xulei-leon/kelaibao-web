# 客来宝网站 SEO 站内分析报告

> 分析对象：`products/kelaibao/` 统一中文官网
> 分析日期：2026-08-08
> 分析类型：基于当前代码、构建产物与本地 HTTP 输出的站内 SEO 审计
> 结论边界：本报告不包含真实生产域名、搜索引擎后台、外链、排名、线上日志或真实用户 Core Web Vitals 数据，不承诺收录或排名。

## 1. 执行摘要

客来宝当前不是“缺少 SEO 基础设施”，而是“技术基础较完整，但生产可索引条件、搜索需求覆盖和信任内容尚未闭环”。

站点已经具备企业官网中较好的技术基线：公开页面服务端输出 HTML；静态页面拥有独立 Title、Description、Canonical、Open Graph；存在全局结构化数据；新闻和案例支持 SSR、文章级 metadata、JSON-LD、404/410；存在 robots、动态 Sitemap、RSS、实验性 `llms.txt`；旧路由使用永久重定向；管理后台和健康检查明确禁止索引。

当前最重要的 SEO 问题不是继续堆技术标签，而是以下四项：

1. **生产索引仍被有意阻断。** 默认环境会输出全站禁止抓取或 `noindex`；正式域名、备案、真实二维码、专业审查及其他发布门禁尚未完成时，这是正确行为，但也意味着当前阶段不能期待自然搜索增长。
2. **非品牌搜索意图覆盖偏弱。** 现有核心页面标题多为“核心工具”“团队解决方案”“媒体中心”等站内导航语言，未充分表达“直销拓客工具、团队小程序、数字化展业、媒体发稿”等潜在查询意图。
3. **可持续内容与实体信任不足。** 新闻/案例能力已经建好，但当前代码和本地环境无法证明存在足够的已发布内容；同时多项强宣传口径需要外部证据支持。对直销、大健康等高信任要求领域，这会直接影响用户与搜索系统对内容可靠性的判断。
4. **发现文件和 CMS 共用运行依赖。** Sitemap、RSS、`llms.txt` 每次生成都读取数据库；数据库不可用时返回 503。该设计会正确暴露故障，但上线前必须有监控、缓存与发布探测，避免 robots 已允许抓取而发现文件不可用。

综合判断：

| 维度 | 当前判断 | 说明 |
| --- | --- | --- |
| 抓取与索引技术 | 较好，但尚未生产闭环 | 代码能力完整；真实域名、数据库和索引开关仍是外部门禁 |
| 页面语义与 metadata | 较好 | 唯一 Title、Description、Canonical 和单一 H1 已落实 |
| 信息架构与内链 | 中等 | 主路径清楚，但案例入口弱，核心页之间的语义内链不足 |
| 结构化数据 | 中等 | 已有 Organization、WebSite、BreadcrumbList、Article；实体字段和页面类型仍偏薄 |
| 内容与搜索需求覆盖 | 偏弱 | 以品牌和销售叙事为主，缺少经过验证的非品牌主题集群 |
| 信任与可核验性 | 上线阻断项 | 正式主体、备案、声明证据、作者/审核机制等仍需真实输入 |
| 性能 | 基线尚可，图片有风险 | JS 体积可控；全局关闭图片优化，功能页图片总量较大 |
| 数据衡量 | 未知 | 代码仅证明可发送匿名分析事件，未见真实搜索平台与线上数据 |

## 2. 分析方法与验证范围

本报告按照以下 SEO 因果链检查：

`可访问 -> 可抓取 -> 可索引 -> 可理解 -> 与搜索意图相关 -> 值得信任 -> 使用体验良好 -> 可衡量和持续改进`

已执行的验证：

- 通过代码知识图谱梳理公开路由、metadata、结构化数据、内容发布和发现文件调用关系。
- 检查 App Router 与 Pages Router 的公开页面、导航、页脚、标题结构、图片配置、重定向和 CMS 输出。
- 运行 `pnpm test`：62 个测试文件、349 项测试全部通过。
- 运行 `pnpm lint`：TypeScript 无输出检查通过。
- 以隔离的示例 HTTPS Origin 和生产索引配置运行 `pnpm build`：构建成功。
- 启动 standalone 产物并通过本地 HTTP 请求检查关键页面、robots、发现文件和旧路由响应。

本次未验证：

- 正式生产域名是否已经上线、ICP备案及主体信息是否完整。
- Google Search Console、Bing Webmaster Tools、百度搜索资源平台的收录与查询数据。
- 线上 ESA/FC/RDS/OSS 的真实可用性、缓存命中和搜索引擎日志。
- 真实外链、品牌提及、关键词搜索量、竞争强度和当前排名。
- 线上 Lighthouse、CrUX、真实用户 Core Web Vitals。
- 宣传数字、媒体渠道、客户案例、Logo、资质或专业审核的外部证明。

因此，报告中的关键词方向均为**待验证假设**，不能替代真实关键词研究。

## 4. 已确认的优势

### 4.1 服务端可抓取 HTML

首页、功能、团队、媒体、关于和政策页为静态预渲染；新闻和案例使用服务端渲染。正文、链接和标题不依赖浏览器执行 JavaScript 后才出现，适合百度、Bing、Google 以及多数 AI 抓取器理解。

本地 HTTP 检查确认九个核心静态页面均返回 200、一个 H1 和一份全局 JSON-LD。

### 4.2 索引策略有明确门禁

Preview 默认禁止抓取；只有同时满足生产环境与 `production-approved` 状态才允许索引。后台、API 和健康检查具有单独的禁止索引或 robots 规则。这种“默认关闭、明确放行”的策略能避免预览站、测试数据或后台页面误入索引。

### 4.3 Canonical 与 metadata 基线完整

核心页面拥有唯一的中文 Title、Description 和自指 Canonical，Open Graph URL 由统一站点 Origin 生成。新闻和案例详情也基于不可变 slug 生成绝对 Canonical，包含发布时间和更新时间。

### 4.4 内容生命周期对 SEO 友好

CMS 只公开已发布 revision；草稿不会泄漏。详情不存在时返回 404，已下线内容返回 410；发布和下线会生成精确的缓存刷新任务。这比始终返回 200 的“软 404”更有利于搜索引擎理解内容状态。

### 4.5 发现与机器可读输出齐全

站点实现了：

- `/robots.txt`
- `/sitemap.xml`
- `/feed.xml`
- `/llms.txt`
- Organization、WebSite、BreadcrumbList、NewsArticle/Article JSON-LD

`llms.txt` 目前仍是实验性发现文件，不应被当作排名或 AI 引用手段；其价值低于正常 HTML、内链、Sitemap 和高质量内容。

### 4.6 基础语义与图片可访问性较好

公共页面普遍使用单一 H1、分区 H2/H3、`article`、列表、面包屑和 `time`。19 个登记视觉素材均有尺寸和非空替代文本，可降低布局偏移并改善图片语义。

## 5. 主要问题与建议

### P0：上线前必须关闭的门禁

#### P0-1 生产站当前不具备可索引结论

**状态：已确认的产品门禁，不是代码缺陷。**

默认配置为 Preview 和 `blocked`，会阻止全站抓取或给动态内容输出 `noindex`。现有项目文档同时表明正式域名、ICP备案、真实二维码、专业审查和若干云环境证据尚未闭环。

建议在允许索引前使用真实 HTTPS 域名完成一次发布后验收，至少验证：

1. 首页、`/features`、`/team`、`/media`、`/news`、一篇新闻详情和一篇授权案例详情均为 200。
2. 所有页面的 Canonical 均指向同一正式 Origin，不出现示例域名、Preview 域名、FC Origin 或 HTTP。
3. 静态 App Router 页面与动态 Pages Router 页面均输出 `index,follow`。
4. `/robots.txt` 允许公开路径并声明正式 Sitemap。
5. Sitemap、RSS 和 `llms.txt` 均为 200 且内容使用正式 Origin。
6. `/admin`、`/api`、`/health` 保持禁止索引。

#### P0-2 构建期与运行期索引配置必须完全一致

**状态：已确认的配置风险。**

静态页面的 metadata 在构建时生成，新闻/案例页面在请求时根据运行环境生成。本地验证中，使用生产索引配置构建、再用 Preview 运行 standalone 后，静态页面输出 `index,follow`，而 `/news` 和 `/cases` 输出 `noindex,nofollow`。该结果来自故意制造的环境差异，但证明同一产物存在“页面类型之间索引状态不一致”的可能。

建议：

- 部署系统对 `NEXT_PUBLIC_SITE_ENV`、`NEXT_PUBLIC_SITE_URL` 和 `PUBLIC_CRAWL_STATUS` 执行构建期/运行期一致性校验。
- 发布后不要只检查首页；必须同时检查一个静态页面、一个列表页和一个详情页。
- 若发现不一致，整次发布失败，不允许开启 robots。

#### P0-3 发现文件依赖数据库健康

**状态：代码行为已确认；生产影响待真实环境验证。**

Sitemap、RSS 和 `llms.txt` 每次都会并行读取已发布新闻和案例；数据库或仓储不可用时返回 503。本地 standalone 未配置生产数据库时，三者均按设计返回 `Discovery output is unavailable.`。

建议：

- 将 `/sitemap.xml` 200、XML 可解析和正式 Origin 校验加入发布探测与持续监控。
- robots 允许抓取前，要求公开页面和发现文件同时健康。
- 在 ESA 保留合理缓存，并评估“最后一次成功生成结果”的安全降级方案；不得在故障时输出空 Sitemap 伪装成功。
- 数据库告警必须覆盖发现文件，而不只覆盖管理后台和详情页。

### P1：最优先的自然搜索增长项

#### P1-1 页面标题更像导航名称，而不是搜索需求答案

**状态：已确认。**

`/features` 的“核心工具”、`/team` 的“团队解决方案”、`/media` 的“媒体中心”脱离站点上下文后语义过宽。搜索结果首先展示 Title，Title 应让用户立即判断页面解决什么问题。

建议先做一次真实关键词研究，再确定最终文案。可测试的初始假设如下：

| 页面 | 假设性主搜索意图 | Title 方向示例 | H1 方向示例 |
| --- | --- | --- | --- |
| `/` | 直销拓客工具、数字化展业工具 | 客来宝 K-Link｜直销拓客与团队数字化工具 | 一站式直销拓客与团队数字化工具 |
| `/features` | 数字名片、内容工具、客户经营工具 | K-Link 核心功能｜内容工具、数字名片与团队小程序 | 从曝光到沉淀的直销拓客工具 |
| `/team` | 直销团队管理、团队小程序、内容复制 | 直销团队小程序与数字化赋能方案｜K-Link | 让团队内容、分享与客户归属可复制 |
| `/media` | 媒体发稿、品牌新闻稿、团队 IP | 媒体发稿与团队 IP 内容服务｜客来宝媒体 | 从社交传播到可核验的媒体内容 |

这些只是页面定位示例，不能未经搜索量、竞争页面和合规审核直接上线。避免把多个近义词机械堆入 Title。

#### P1-2 缺少非品牌主题集群和持续更新的入口内容

**状态：内容数量外部未知；代码层面确认只有新闻和案例两类 CMS。**

现有核心页面主要承担产品销售叙事。仅靠品牌页很难覆盖处于问题识别、方案比较和风险评估阶段的搜索用户。新闻 CMS 的 metadata 已允许“方法说明与市场观察”，可以在不增加 CMS 类型的前提下承担早期内容增长。

个人创业阶段建议先做最小内容集，不追求高频批量发布：

1. 直销从业者如何整理可信的个人数字名片。
2. 团队小程序如何统一内容，同时保留成员分享归属。
3. 直销团队资料如何版本统一、持续更新和合规审核。
4. 媒体发稿的一般流程、审核边界和影响费用的因素。
5. 团队 IP 内容如何区分事实、观点、案例和效果声明。
6. 一篇有授权、说明背景与过程、不过度归因的真实案例。

每篇内容应服务一个明确问题，并链接到最相关的产品页或服务页；产品页也应反向链接到对应解释内容，形成主题闭环。

#### P1-3 `/cases` 的发现路径不完整

**状态：已确认，且当前测试明确要求页脚不出现案例入口。**

案例列表和详情能力存在，但 `/cases` 不在主导航、页脚或 `PUBLIC_ROUTES` 核心 Sitemap 清单中。已发布案例详情会进入动态 Sitemap，详情面包屑也会指回 `/cases`；然而在没有案例详情时，案例列表接近孤立页面。

建议根据真实案例授权状态二选一：

- **尚无可公开案例：** 继续隐藏 `/cases`，并考虑对空列表保持 `noindex,follow`，不要在 Sitemap 中宣传空页面。
- **已有足够授权案例：** 将 `/cases` 纳入 Sitemap，并至少从 `/about`、`/team` 或页脚提供一个上下文明确的入口；不一定要增加主导航项。

不要为了 SEO 发布虚构、弱授权或无法解释结果归因的案例。

#### P1-4 实体与信任信号尚未闭环

**状态：外部证据缺失。**

About 页面已经展示“100+”“10万+”“100万+”“0 隐私采集”“100% 私域归属”等口径；媒体页面包含“百家主流媒体全覆盖”和具体媒体名称；团队页面包含效率、转化与增长表达。这些不一定错误，但对于直销与大健康相关业务，搜索系统和用户会要求更强的可核验性。

上线前建议：

- 对每个量化口径保存统计口径、时间范围、数据来源和批准人。
- 若无法公开证明，改成可验证的事实陈述或删除绝对化表达。
- 在 About/页脚补充已确认的经营主体、联系地址、公开联系方式、备案信息和适用资质；不得使用占位值。
- 新闻和方法文章显示真实作者或负责团队、发布日期、更新时间、引用来源和纠错方式。
- 涉及健康、收益、转化率、客户归属和隐私技术的内容，增加相应专业审核与证据记录。

这既是合规问题，也是 SEO 的信任基础；结构化数据不能替代真实页面证据。

### P2：技术与页面增强项

#### P2-1 静态页面结构化数据过于基础

**状态：已确认。**

静态页面只复用字段较少的 Organization 和 WebSite；Organization 目前主要包含名称和 URL。新闻/案例拥有 BreadcrumbList 与 Article，但文章缺少图片字段，Open Graph 也没有文章图片。

建议按真实页面语义逐步补充：

- Organization：正式 logo、合法名称、经确认的联系信息和官方账号 `sameAs`。
- 首页：WebPage；若 K-Link 产品事实足够，可评估 Product 或 SoftwareApplication，不能虚构价格、评分或下载信息。
- `/media`：Service，清楚描述服务提供方、区域和服务类型。
- `/about`：AboutPage。
- 核心静态页：可见面包屑与 BreadcrumbList 保持一致。
- 新闻/案例：补充代表图片、`isPartOf`、适当的文章分类；图片必须真实存在并可公开抓取。

只有页面上真实可见、可验证的内容才应进入 JSON-LD。FAQ 应先做成用户可见内容；不要把 FAQ schema 当作富结果保证。

#### P2-2 图片传输存在优化空间

**状态：已确认的资源风险，未证明 Core Web Vitals 已失败。**

构建配置全局启用 `images.unoptimized: true`。功能页十张功能图片合计约 5.97 MB，单张最高约 1.23 MB；全部公开资源约 12.69 MB。图片已有宽高、WebP、`sizes` 和懒加载基础，Hero 也设置了优先加载，因此布局稳定性基础较好；但关闭图片优化后，不同视口通常仍会下载同一个原始文件，`sizes` 无法充分转化为响应式字节节省。

建议：

- 为 320、390、768、1440 等实际展示宽度预生成响应式 WebP/AVIF，并输出 `srcset`，或验证 FC/ESA 上可安全启用图片优化。
- 将首屏 Hero 与非首屏图片分别设定体积预算；非首屏仍需控制总滚动流量。
- 上线后分别在大陆移动网络与微信内置浏览器测量 LCP、INP、CLS，不能只看本机构建大小。
- 大图 Lightbox 当前按点击加载的设计可以保留，但应确认移动端不会提前下载 3.5 MB 办公室图片。

构建报告显示 App Router 公开页首屏共享 JS 约 102 KB，单页 First Load JS 约 112–116 KB；Pages Router 新闻/案例约 114 KB。该体积不构成已确认故障，但仍应由真实 CWV 决定是否继续削减客户端 Provider 和交互脚本。

#### P2-3 内容列表和发现文件存在 100 条上限

**状态：条件性风险。**

数据库对每种内容最多读取 100 条；发现文件合并新闻和案例后再次截取到最新 100 条。列表没有分页。内容规模超过上限后，旧内容可能从列表和 Sitemap 消失，只能依赖历史外链或直接 URL 被发现。

建议在接近 60–80 条公开内容前规划：

- 新闻和案例列表分页，并提供可抓取的分页链接。
- Sitemap Index 或按内容类型拆分 Sitemap。
- Sitemap 覆盖全部有效公开 URL，而不是仅最新 100 条。
- 下线内容继续使用 410，避免旧内容与新内容混杂。

当前内容量若很小，无需为了未来规模立即增加复杂度，但应建立阈值提醒。

#### P2-4 内链应从“导航可达”升级为“语义相关”

**状态：已确认改进空间。**

当前全站导航和页脚保证主要页面可达，但正文中的上下文链接较少。搜索引擎除了看菜单，还会根据正文锚文本理解页面关系。

建议：

- 首页四组工具分别链接到 `/features` 对应稳定锚点。
- `/features` 的团队小程序、品牌专刊等功能链接到 `/team` 的相关说明。
- `/media` 链接到解释发稿流程、审核边界和团队 IP 的新闻文章。
- `/about` 在存在授权案例后链接到 `/cases`，并保留新闻入口。
- 新闻详情增加“相关功能/相关服务/相关阅读”，但必须人工选择，避免全站重复推荐。

锚文本应描述目标内容，例如“查看团队小程序如何保留成员分享归属”，而不是重复使用“了解更多”。

#### P2-5 新闻列表存在重复配置和轻微语义漂移

**状态：已确认，影响较低。**

`ROUTE_METADATA`、动态列表 metadata 和列表组件分别维护新闻名称/描述；当前 Title 基本一致，但 H1 为“新闻中心”，配置名称为“新闻动态”，描述也有两个版本。长期修改时容易发生 Title、H1、Sitemap 和页面定位不一致。

建议将新闻/案例列表的标题、描述、路径和结构化数据标签收敛为单一配置源，或增加跨实现一致性测试。

### P3：上线后的运营增强

#### P3-1 建立搜索平台和指标基线

**状态：外部未知。**

代码存在可选匿名分析 endpoint，但这不能替代搜索引擎数据。正式域名上线后至少接入：

- 百度搜索资源平台。
- Bing Webmaster Tools。
- Google Search Console（若海外或跨境用户仍是目标受众）。

个人创业阶段建议只维护一张月度表：

| 指标 | 用途 |
| --- | --- |
| 有效索引页面数 | 判断技术发布是否正常 |
| 非品牌曝光与点击 | 判断是否真正拓展新需求 |
| 各落地页查询词 | 决定 Title、内容和内链迭代 |
| 合格咨询数及落地页 | 判断 SEO 是否贡献业务，而非只看流量 |
| Sitemap/抓取错误 | 发现数据库、Origin 和状态码问题 |
| LCP、INP、CLS | 决定性能优化优先级 |

所有提交接口应直接使用明确的 HTTP(S) API，不增加通用 `webservice` 抽象。

#### P3-2 静态页更新时间和社交分享可继续完善

核心静态 URL 在 Sitemap 中没有 `lastmod`。这不是排名阻断项；如果未来要添加，必须来自真实内容变更时间，不能每次部署都伪造为当前时间。还可为新闻/案例设置独立 Open Graph 图片，并按实际渠道决定是否添加 Twitter Card 等社交 metadata。

## 6. 推荐的最小执行顺序

### 阶段 A：生产上线前

1. 完成真实域名、备案、主体、二维码、专业审查和声明证据门禁。
2. 保证构建期和运行期的站点 Origin、环境和索引状态一致。
3. 在真实 RDS 下验证 Sitemap、RSS、`llms.txt` 和一篇新闻/案例详情。
4. 对量化、绝对化、媒体覆盖和增长类口径完成证据审查。
5. 注册搜索平台，但在验收通过前不提交 Sitemap、不解除抓取阻断。

### 阶段 B：上线后首轮站内优化

1. 用真实关键词数据确定首页、功能、团队和媒体页的唯一主意图。
2. 调整 Title、H1、首段和正文语义，保持自然表达。
3. 决定 `/cases` 是继续隐藏还是形成正式入口。
4. 补齐 Organization 实体信息和新闻/案例图片 metadata。
5. 优化功能页响应式图片并取得移动端性能基线。

### 阶段 C：30–60 天内容验证

1. 发布 4–6 篇高意图、可核验的解释内容，而不是追求日更。
2. 每篇内容连接到一个核心商业页，并配置相关阅读。
3. 有真实授权后发布 1–3 篇案例，清楚区分事实、过程和不可归因结果。
4. 根据搜索查询词和合格咨询调整主题；没有曝光的主题不继续批量扩写。

## 7. 验收清单

### 抓取与索引

- [ ] 正式域名仅有一个 HTTPS Canonical Origin。
- [ ] 静态页、列表页、详情页索引状态一致。
- [ ] robots 允许公开路径，禁止后台和 API。
- [ ] Sitemap 为 200、可解析、包含全部应公开 URL。
- [ ] Preview、FC Origin 和测试域名均不可索引。
- [ ] 404、410、308 在正式 ESA/FC 链路保持正确。

### 页面与内容

- [ ] 每个核心页只有一个主搜索意图。
- [ ] Title、H1、首段和正文回答同一意图。
- [ ] 所有量化和绝对化口径有证据或已降级表达。
- [ ] 新闻有作者/责任团队、日期、来源和更新机制。
- [ ] 案例具有真实授权并说明结果边界。
- [ ] 正文内链使用有意义的锚文本。

### 技术与体验

- [ ] Organization/Service/Article JSON-LD 与页面可见事实一致。
- [ ] 新闻和案例拥有可抓取的代表图片。
- [ ] 移动端图片使用合适尺寸，而非统一下载原图。
- [ ] 大陆网络与微信浏览器的 LCP、INP、CLS 已记录。
- [ ] Sitemap/数据库失败有告警和可恢复方案。

### 衡量

- [ ] 百度、Bing、Google（如适用）完成站点验证。
- [ ] 提交正式 Sitemap 并记录首次收录基线。
- [ ] 区分品牌词与非品牌词。
- [ ] 能将合格咨询关联到入口页，不记录询盘正文等敏感信息。

## 9. 最终结论

客来宝已经具备“可做 SEO”的工程基础，但尚未具备“SEO 已经生效”的证据。短期最高回报不是增加更多技术文件，而是完成生产索引门禁、统一构建/运行配置、保证 Sitemap 数据依赖健康、把核心页面改造成明确的非品牌搜索落地页，并用少量可核验内容建立主题与信任。

在这些前提完成之前，任何排名、收录或 AI 引用判断都应标记为未知；在这些前提完成之后，再由真实查询数据决定内容投入，而不是按通用 SEO 清单盲目扩张。
